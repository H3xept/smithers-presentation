Smithers v0.31.0 — command reference

Smithers is a durable control plane for long-running coding agents: workflows are TypeScript/JSX graphs that run for minutes or days, persist every finished node, and resume after a crash. The CLI is the operator surface over that runtime. Every command takes --format toon|json|yaml|md|jsonl, --schema, --filter-output, and the --token-count/--token-limit/--token-offset trio. --json is accepted everywhere as shorthand for --format json, with one wrinkle worth knowing: after events, timeline, tree, diff, output, rewind, snapshots and restore it is command-scoped and emits that command's raw JSON payload instead of the standard envelope.

What smithers observability is for

One command, two flags — it is a Docker Compose launcher, not a Smithers subsystem.

Purpose: start (or tear down) a local telemetry stack through Docker Compose — Grafana on :3001 (dashboards, anonymous viewer, admin password admin), Prometheus on :9090 (metrics), Tempo on :3200 (traces), Loki on :3100 (logs — in the compose file, though --help does not mention it), and an OTLP Collector on :4317/:4318 (ingest; Smithers exports to the HTTP port). A run only exports when you set both SMITHERS_OTEL_ENABLED=1 and OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318; the service name defaults to smithers unless you set OTEL_SERVICE_NAME. 
# bring the stack up in the background
smithers observability --detach

# stop and remove it
smithers observability --down
--detach, -dRun the containers in the background instead of attached.
--downStop and remove the observability stack.

You reach for it when a run needs dashboard-level proof rather than a log tail: node throughput and duration across a wide fan-out, success rate, and token totals split by model, with links you can paste into an evidence report. It is complementary to, not a replacement for, the built-in surfaces:

Measured caveat, v0.31.0: with OTel enabled, metrics and logs reach the collector but spans do not reach Tempo — GET :3200/api/search returns {"traces":[]} on a run whose metrics Prometheus holds in full. The dashboard's Traces row stays empty. Plan your evidence around the metric panels and smithers inspect --pool, not around a span waterfall. Active Runs, Active Nodes and the Tools row are live gauges and read No data once a run has finished.

Day-to-day

ps, status, inspect, events, logs, why — enough for almost all local operating.

Raw metrics endpoint

smithers up wf.tsx --serve --port 7331 exposes /metrics for Prometheus without the full stack — --metrics is already on by default with --serve.

Full stack

smithers observability when you want dashboards, metric history, and log search retained across many runs.

Library side

smithers-orchestrator/observability — OTel traces, metrics, Prometheus rendering, custom event sinks.

Caveat: the feature matrix marks observability as status partial, tier platform — partial meaning "the capability ships, but its feature record lists an unproved environment, provider path, or explicit limitation". Expect the tracing surface to be less polished than the run-control commands, and it requires a working Docker daemon.

Run a workflow

The core loop: author → render → launch → watch.

initInstall the local workflow pack into .smithers/; optional prompt also launches the builder.
workflowDiscover local workflows in .smithers/workflows.
make-workflowBuild a new workflow from a plain-English description (dispatches create-workflow).
graphRender the workflow graph without executing — the dry-run / sanity check; must exit 0.
upStart an execution. -d detached, --interactive for the full-screen TUI picker+monitor.
oneshotRun one well-scoped goal with a strong agent in the background, optional review + live UI.
chat-createCreate and start a one-task auto-hijacked chat run.
startersPlain-English starter workflows with copy-paste commands.
reviewCode review + story-form HTML walkthrough for a repo or PR.
upgradeAgent-assisted Smithers upgrade workflow (cheap agent first, escalate if needed).

Control a run

Lifecycle, human gates, and retries.

Time travel & durability

Every finished node is a checkpoint, so you can move backwards.

snapshotsList durability snapshots (workspace checkpoints) for a run.
timelineExecution timeline for a run and its forks.
forkBranch a new run from a snapshot checkpoint.
replayFork from a checkpoint and resume execution.
rewindRewind a run to a previous frame.
restoreRestore a worktree to a durability checkpoint (latest, or --seq).
revertRevert the workspace filesystem to a previous task attempt's state.
timetravelCombined: revert filesystem + reset DB state to a prior task, optionally resume.
worktreeInspect and reclaim worktrees created for <Worktree> lanes.

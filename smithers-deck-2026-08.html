The one-liner, theirs not mine

“Durable AI workflow orchestration
as a JSX runtime.”

A workflow is a TypeScript JSX tree in your repo. It runs for minutes or days. Every finished step is persisted the moment it finishes, so a crash resumes at the last completed node instead of starting over. A run waiting on a human is a row in a database, not a process — it costs nothing while it waits.

The whole mental model, once

Every frame asks one question:
what can run now?

Smithers re-renders your workflow tree every frame against persisted state. Runnable nodes dispatch a real coding agent; the output is validated against a Zod schema, written to a row, and the tree renders again. Completed nodes are skipped — never re-run.

render the tree→ what's runnable?→ dispatch an agent→ validate w/ Zod→ persist the row↺

That is the entire trick. Retries, approvals, loops, worktrees, evals, time travel — all of it is a component composed over that.

// this is why it's JSX and not YAML: the graph is a function of state, so it can be conditional, mapped over data, and typed.

Benefit 1 · the one that matters most

Every finished node is a row.

The run is not a process — it's a table of frames. Kill the machine mid-run, restart, and it picks up at the node it was on. Nodes 01 and 02 are never paid for twice.

An always-on agent that restarts from scratch after a crash isn't autonomous. It's a very expensive random number generator.

How you actually use it

Three routes in. Take the lightest one that keeps the durability you need.

TIER 0
Direct
One typo, one rename, under ~10 agent turns. No orchestration earns its keep here.
// just do it
TIER 1
Oneshot
One clear goal, one strong agent. Nothing to author — background run, live UI, chat / diff / pause / hijack.
smithers oneshot "<goal>"
TIER 2
Workflow
Order, retries, approvals, loops, several models — or reuse. One executable graph per file.
smithers up wf.tsx --interactive

If a procedure recurs, that's the argument for a workflow over a skill. A skill is static prose an agent re-interprets every time. A workflow is executable, durable, typed, inspectable — and measurable.

No .smithers/, no TSX, no schema. It picks a strong agent, runs in the background, and gives you the durable surface for free.

  • runs detached — close the terminal, it keeps going
  • live UI — status, execution tree, streamed chat, diff
  • pause / hijack — park it, or resume the session yourself in your own harness
  • optional review — --review on adds a reviewer pass

This is the on-ramp. If oneshot is enough, you never write a graph.

The part that surprised me

You are not the operator.
Your agent is.

Smithers ships two documentation sets: a human one, and an agent one. The agent-facing docs open with a directive — “the human talks to an AI harness; the AI runs Smithers. Do not ask the human to run commands directly.” Installing is the one step you do by hand.

“Don't stop until this is production-ready.” · “Prove this third-party service works.” · “Show me it works.” · “What happened to that run?”

your agent does

Encodes tests, a reviewer gate and evals as the finish line. Watches the run, reads why / events / scores, and reports evidence back in plain English.

Demo 2 · authoring live

Don't hand-write the first draft. Have it written.

# 1. one-time: seed .smithers/ into the repo
$ smithers init --yes

# 2. describe the outcome in English
$ smithers make-workflow "watch a compose PR
    and auto-land it once CI is green"

# 3. the sanity check. must exit 0.
$ smithers graph .smithers/workflows/land-pr.tsx

# 4. run it, watch it in a full-screen TUI
$ smithers up land-pr --interactive

# 5. or in the browser, over every run
$ smithers monitor

make-workflow is itself a workflow. It clarifies your request into a spec, pulls the relevant docs and skills, designs the graph, pauses for your approval, scaffolds the .tsx and .mdx, then loops on graph until it renders.

The default authoring path afterwards isn't TypeScript at all — it's editing a plain Markdown prompt in .smithers/prompts/. You drop to JSX when you need branching, fan-out, or loops.

A bootstrapping orchestrator: the first graph you run is the one that writes graphs.

What it produced

Isolate → fan out → loop until green → ask a human.

export default smithers((ctx) => (
  <Workflow name="triage-and-fix">
    <Worktree path=".wt/fix" branch="fix/flaky-e2e">

      {/* fan out: one reviewer per dimension, 4 in flight */}
      <Parallel maxConcurrency={4}>
        {DIMENSIONS.map((d) => (
          <Task key={d.id} id={`review-${d.id}`} output={outputs.findings} agent={reviewer}>
            <ReviewPrompt dimension={d} diff={ctx.input.diff} />
          </Task>
        ))}
      </Parallel>

      {/* the "loop": one bounded node with a real stop condition */}
      <Loop until={(ctx) => ctx.latest(outputs.gate)?.green === true} maxIterations={8}>
        <Task id="fix"  output={outputs.patch} agent={implementer} />
        <Task id="gate" output={outputs.gate}  agent={e2eRunner} scorers={scorers} />
      </Loop>

      {/* the human only sees the risky ones */}
      <ApprovalGate id="ship" output={outputs.decision} when={risk === "high"}
        request={{ title: "Land the fix?", summary }} onDeny="skip" />

    </Worktree>
  </Workflow>
))

// control flow, isolation, concurrency, termination, scoring and the human gate — one reviewable file, in the repo, next to the code it operates on.

Benefit 2 · the part autonomy talk skips

Waiting for a human is a first-class state.

“Fully autonomous” is a marketing position, not an engineering one. Real graphs stop and ask. The only question is whether stopping is cheap.

In a loop, waiting three days for a human means a process pinned open for three days. In a graph the run parks durably: zero tokens, zero compute, resumable from a CLI call, an RPC, or a button in the UI.

A gate that costs nothing to wait at is a gate you'll actually use.

  • <ApprovalGate> — a gate you declared up front; deny can fail, skip, or continue
  • ask-human — an agent stuck mid-task raises a durable question and blocks. Exit 0 with the answer, non-zero on deny or timeout
  • <Signal> / <WaitForEvent> — park until CI, a webhook, or a correlated payload arrives
  • <Timer> — a durable sleep, not a held thread
$ smithers why <run>       # why is it blocked?
$ smithers human inbox
$ smithers approve <run> --node ship --by leo

Benefit 3 · the payoff of persisted state

Watch it live. Then rewind, fork, replay.

Once a run is a sequence of frames with a VCS pointer attached, “what if the reviewer had been stricter?” stops being a re-run from zero and becomes a branch.

fork

alternate timeline

Branch an independent run from an earlier checkpoint. The original stays intact, so you can compare.

replay

re-execute

Run forward again from a checkpoint, optionally restoring the worktree to match it.

rewind

in place

Roll the active run back to a previous frame and continue from there.

restore

filesystem

Reset the working tree to a durability snapshot — the files, not just the rows.

$ smithers timeline <run>     # frames, forks, checkpoints
$ smithers node <run> gate     # retries, tool calls, output
$ smithers what <run>         # a cheap agent narrates what happened
$ smithers fork <run> --seq 42  # stand at the frame it went sideways

You stop guessing why a run went wrong and go stand at the frame where it did.

Benefit 4 · the one that compounds

Prompt iteration, with teeth instead of vibes.

The reason we all fiddle with prompts is to make the agent better at a task. A workflow gives that loop a number, because every run is already a labeled example: this prompt, this context, these tools → this trace, this outcome.

A loop has no score. A graph has a score per node.

// honest caveat: field-wide eval-driven development for coding agents is still under-evidenced. There's no settled playbook — but a regression suite beats a hunch.

$ smithers eval wf.tsx \
    --cases evals/suite.jsonl --suite smoke

$ smithers scores <run>

# GEPA searches prompt variants against the suite
$ smithers optimize wf.tsx --cases evals/suite.jsonl
  • five built-in scorers — schema adherence, latency, relevancy, toxicity, faithfulness
  • llmJudge(...) — a rubric on any task
  • they never block — sample the expensive ones with ratio
  • memory — cross-run facts, so run N+1 knows what run N learned

The vision · the problem it creates

24/7graphs × repos × triggers

Graphs are token furnaces.

Nightly research. PR babysitting. Issue triage. Drift detection. Perf work. The moment durability makes always-on possible, you discover an enormous volume of in-flight tokens — every one of them billed on a frontier API.

Success at graph engineering is, today, a cost problem.

The vision · the escape hatch

Good decomposition → small models.

Here's the thing the graph does to the work that nothing else does. It breaks a vague, unbounded objective into nodes that are bounded, typed, and individually verifiable:

  • score this finding
  • verify this claim against the diff
  • triage this ticket into a lane
  • summarize this trace
  • run the suite and report structured failures

That is exactly the shape of work a self-hostable model is already good enough to do — and a Zod schema plus a scorer catches it when it isn't.

The orchestration, the verification and the budget that keep a small model honest live in the graph around it. Per-node routing is what lets you actually spend the cheap model.

// sandwich delegation: expensive models plan and review at the ends, cheap models implement the middle.

The vision · the pivot

From renting tokens to renting hardware.

Decomposition put the bounded work within reach of a model small enough to run yourself. Kimi's open-weight MoE flagship is documented, in Smithers' own model notes, as “the strongest model you can self-host.” So the question opens up: what if you hosted it?

today · rent tokens

Frontier API

Pay per token. The meter runs only when you do — zero ops, scales with use — but every always-on graph bills forever.

the move · rent the box

Your own rig

Pay by the hour for GPUs. Fixed whether idle or flat out — so the whole game becomes keeping them busy.

That flips cost from variable to fixed. Whether it pays comes down to one number: sustained throughput.

The vision · the arithmetic point-in-time

Saturate the rig — or the API wins.

A rented cluster bills the same serving one request or a million; the API bills only tokens. Break-even is therefore a rate you must hold around the clock — and a well-tuned node clears it by 6–24×.

self-host wins when sustained TPS > hourly cost ÷ ($/tok × 3600)

The vision · and here is the punchline

Self-hosting is three lines in agents.ts.

  api: "chat",                 // not /responses

  tools,
})

This is why the seam matters. Self-hosting isn't a rewrite, a migration, or a platform decision — it's a per-node decision, made in one file, and graded by an eval suite you already have.

If you remember three things

Persist it. Gate it. Bind late.

Durable beats autonomous.Every finished node is a row. Crash-resume, rewind, fork and replay are the difference between an agent that runs for days and one that merely starts for days.
Stopping to ask must be free.A parked run is a row, not a pinned process. Approvals and ask-human cost nothing to wait at, which is the only reason anyone puts them in.
The node is the unit of cost — and of freedom.Bind the engine per role in one file. That's how you spend a cheap model where it's safe, and it's how self-hosting becomes an incremental, measurable decision instead of a bet.

Start absurdly small: smithers oneshot "<the thing you were going to babysit anyway>". If you run it twice, make it a graph.

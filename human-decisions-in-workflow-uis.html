Human decisions in workflow UIs

An approval gate renders nothing. It persists a row and parks the run. A custom workflow UI is one of three clients that can clear that row — and the only link between your graph and your UI is a pair of matching id strings.

  1. What the gate actually is, and why the UI is optional
  2. Making a human decide, three levels of effort
  3. The exact payloads — and the two gotchas
  4. Yes/no vs. structured input: pick the right node
  5. Multi-select: yes, via rank

01What the gate actually is

<Approval> has no visual component. It is a scheduler task that, when the graph reaches it, writes a pending decision row keyed on (runId, nodeId, iteration) and stops handing out work in that lane. The process may then exit; the row survives.

That row is readable and writable over exactly one pair of Gateway RPC methods. Everything that clears a gate — the CLI, your UI, an automated keeper — is a client of those two:

DirectionRPC methodREST twinScope
read pendinglistApprovalsGET domain readrun:read
write decisionsubmitApprovalPOST /v1/api/approvals/:idapproval:submit

The UI is not a feature of the gate. It is the third client of a durable row, and it is the only one a non-engineer will ever use.

02Making a human decide, three levels

Level 1 — nothing to write

SimpleWorkflowDashboard is a complete one-workflow dashboard: prompt box and Start button, run list, node tree, structured event log, a live per-node chat pane, and a monitor link. Approvals are already in it.

.smithers/ui/triage.tsx

import { createGatewayReactRoot } from "smithers-orchestrator/gateway-react"
import { SimpleWorkflowDashboard } from "smithers-orchestrator/gateway-ui"

createGatewayReactRoot(<SimpleWorkflowDashboard workflow="triage" />)

Level 2 — drop in an approval widget

Three prebuilt queues, in rising richness. All of them resolve through submitApproval for you:

Level 3 — your own control, two hooks

When the decision needs your product's own layout — a triage table where each row is a ticket — read with useGatewayApprovals and write with useGatewayActions.

.smithers/ui/triage.tsx

import {
  createGatewayReactRoot, useGatewayApprovals, useGatewayActions, useGatewayNodeOutput,
} from "smithers-orchestrator/gateway-react"

function TriageGate({ runId }: { runId: string }) {
  // `data` IS the array of gates — there is no `data.approvals` wrapper.
  const gates = useGatewayApprovals({ filter: { runId } })
  const { submitApproval } = useGatewayActions()

  return (gates.data ?? []).map((g) => (
    <article key={`${g.nodeId}:${g.iteration}`}>
      /* the title field is `requestTitle`, not `title` */
      <h3>{g.requestTitle ?? g.nodeId}</h3>
      <p>{g.requestSummary}</p>

      /* the real context lives in the UPSTREAM node's output — see §03 */
      <TicketList runId={runId} nodeId="classify" />

      <button onClick={() => submitApproval({
        runId, nodeId: g.nodeId, iteration: g.iteration,
        decision: { approved: true },
      })}>Approve</button>

      <button onClick={() => submitApproval({
        runId, nodeId: g.nodeId, iteration: g.iteration,
        decision: { approved: false, note: "not this sprint" },
      })}>Deny</button>
    </article>
  ))
}

useGatewayApprovals re-pulls when a run reaches waiting-approval, and again after a submitApproval invalidates the collection — so the pending list is self-maintaining. The queue only drains once the run is resumed and the next gate is reached; the re-pull reflects that state, it does not cause it. Over WebSocket, submitApproval also auto-subscribes the connection to the affected runId.

Writing the decision is not the same as restarting the run. submitApproval persists the row; if the owning process has exited — which is the whole point of a durable gate — the run stays parked and must be resumed. From a UI that is useGatewayActions().resumeRun({ runId }) right after the submit; from a terminal it is smithers up <workflow> --run-id <run> --resume true. The runtime names this state explicitly: smithers inspect reports runState.blocked.kind === "approval-decided-resume-required" for a decided-but-detached gate, and smithers why prints the exact unblock command.

03The exact payloads — and the two gotchas

A pending gate summary is exactly this shape:

type GatewayApprovalSummary = {
  runId: string
  nodeId: string
  iteration: number
  requestTitle?: string
  requestSummary?: string
  workflowKey?: string
  requestedAtMs: number
}
Gotcha 1 · options reach the UI, arbitrary metadata does not

options are delivered — the Gateway parses them out of the stored request into the approval record, which is how a select or rank UI renders its choices at all. What the typed GatewayApprovalSummary omits is your free-form request.metadata: the hook hands you requestTitle and requestSummary and nothing else. (The MCP list_pending_approvals tool does return the full request as unknown, so the data is on disk — it is the React hook's shape that narrows it.)

Design consequence: use options for the choosable keys, and put the rich per-item context — diffs, ticket bodies, risk — in the upstream task's output, read with useGatewayNodeOutput({ runId, nodeId }) (one object parameter, never positional). Join the two on the option key. That keeps the payload typed by a Zod schema and persisted as a row, which free-form metadata would be neither.

Gotcha 2 · field names bite

The title is requestTitle, not title. The hook's data is the array, not data.approvals. And decision is required on submitApproval — the verdict lives inside that object, not as a sibling approved flag.

04Yes/no vs. structured input

This is the part that decides your graph's shape. Everything below was verified by running it against a live Gateway on v0.31.0, not read off the docs — the docs never spell the decision param type, which is exactly where the confusion lives.

NodeHuman returnsReachable from a browser UI?
<Approval> { approved, note, decidedBy, decidedAt } Yes — listApprovals + submitApproval, plus three prebuilt widgets. verified
<WaitForEvent> / <Signal> an arbitrary JSON payload Yes — submitSignal({ runId, signalName, correlationKey, payload }), payload is unconstrained. verified
<HumanTask> JSON matching the node's Zod output schema No Gateway RPC exists. Of the 41 methods, none answers a human request — the path is the CLI. CLI only

<HumanTask> is the natural-looking choice for “a human fills in a form”, and it is a trap if the form lives in a browser. Its documented resolution path is an operator command:

clearing a HumanTask

$ smithers human inbox                                  # find the requestId
$ smithers human answer <requestId> --value '{"severity":"high"}'

None of the 41 Gateway RPC methods answers a human request. So when the decision is richer than a verdict and must happen in your UI, model it as a signal — the payload is free-form and the write path is fully supported:

.smithers/workflows/triage.tsx

<WaitForEvent
  id="pick-tickets"
  event="triage-choice"
  correlationId="triage-choice"
  output={outputs.choice}
/>

.smithers/ui/triage.tsx

const { submitSignal, resumeRun } = useGatewayActions()

submitSignal({
  runId,
  signalName: "triage-choice",     // must equal the node's `event`
  correlationKey: "triage-choice", // must equal its `correlationId`
  payload: { keys: checked },
})
await resumeRun({ runId })          // the signal fills the row; this wakes the run

Send both keys, and expect no error if you get them wrong. A wait node resolves only when the signal name matches its event and the correlation key matches its correlationId. signalName is optional in the RPC signature and the Gateway defaults it to the correlationKey — which is why this example works at all, and why it breaks the moment the two strings differ, as they do in examples/todo-cli (event="spec.edited", correlationId="spec-then-build-edit"). A mismatch is not a rejected write: the signal is delivered, no waiter matches, and the run sits parked looking perfectly healthy. Import both strings from one shared contract file, the way .smithers/ui/spec-then-build-contract.ts does.

04bMulti-select: yes, via rank

There is no mode="multi-select", which makes it look like a picked set is not expressible. It is. mode="rank" is validated as a non-empty subset of the declared option keys — nothing requires you to rank all of them, and nothing inspects the order. A rank decision carrying two of four keys is a multi-select with a misleading name.

The Gateway's validator is the whole story, and it is eleven lines:

@smithers-orchestrator/server/src/gateway.js · validateApprovalDecision

if (request.mode === "select") {
  const selected = asString(payload?.selected)      // a STRING, or reject
  if (!selected) return { ok: false, message: "select approvals require decision.selected" }
  if (request.options.length > 0 && !request.options.some((o) => o.key === selected))
    return { ok: false, message: `Unknown selection: ${selected}` }
}
if (request.mode === "rank") {
  const ranked = parseStringArray(payload?.ranked)   // an ARRAY of keys
  if (ranked.length === 0) return { ok: false, message: "rank approvals require decision.ranked" }
  const allowed = new Set(request.options.map((o) => o.key))
  if (allowed.size > 0 && ranked.some((v) => !allowed.has(v)))
    return { ok: false, message: "rank approval included unknown options" }
}

Read the rank branch as a set contract: non-empty, and every member is a declared key. No length check against options, no ordering check. So:

.smithers/ui/triage.tsx — a working multi-select

submitApproval({
  runId, nodeId: "subset", iteration: 0,
  decision: { approved: true, value: { ranked: checkedKeys } },  // 2 of 4 is fine
})
verified end to end · v0.31.0

A gate declared mode="rank" with four options alpha·beta·gamma·delta, submitted { ranked: ["gamma","alpha"] }, landed in the workflow's output row as ranked = ["gamma","alpha"], exactly as sent — subset preserved, my order preserved.

The same run submitted { selected: ["alpha","gamma"] } to a mode="select" gate and the Gateway rejected it: INVALID_REQUEST · select approvals require decision.selected. So a multi-select under select fails loudly at the write — it is never silently truncated.

Nested or flat, both work

The TUI sends { approved: true, value: { selected } }; the component reads decision.selected flat. Those agree because the Gateway unwraps one level first:

const decision = stableDecision && "value" in stableDecision ? stableDecision.value : params.decision

So {approved, value:{ranked}} and {approved, ranked} are equivalent on the wire. The stored decision_json is the unwrapped form either way — I confirmed {"ranked":["gamma","alpha"]} on disk.

Where the real ceiling is

Transport is not the limit: the RPC schema declares decision with additionalProperties: true, and persistence is a plain JSON.stringify of whatever survived validation. The limit is in Approval.js, where computeDecision reads the stored row back and narrows it to exactly three shapes:

  • { approved, note, decidedBy, decidedAt } — built field-by-field, so extra keys you submitted are dropped here
  • { selected: string, notes } — typeof … === "string" or ""
  • { ranked: string[], notes } — filtered to strings

This is why a custom outputSchema does not buy you an arbitrary payload in approve mode: the component only ever emits those four fields, so a schema demanding more fails validation rather than receiving more. <Approval> is a three-shape funnel, not a form. When you need a genuinely arbitrary shape — nested objects, per-item fields, free text alongside a set — that is what <WaitForEvent> + submitSignal is for, and its payload has no validator at all.

05The two triage.tsx files

This is the whole connection, and it is smaller than people expect: there are two files named triage.tsx, they never import each other, and the only thing joining them is a pair of matching strings.

file A · the graph

.smithers/workflows/triage.tsx — runs on the server. Contains the <Approval> nodes and one <UI> declaration.

file B · the browser bundle

.smithers/ui/triage.tsx — runs in the tab. The Gateway builds it and serves it at /workflows/triage.

.smithers/workflows/triage.tsx

<Workflow name="triage">
  <UI entry="../ui/triage.tsx" title="Triage" />   // ← link 1: which bundle

  <Task id="classify" output={outputs.tickets} agent={triager}>
    Classify every open Sentry issue into a ticket.
  </Task>

  <Approval
    id="triage-approve"                          // ← link 2: the nodeId
    output={outputs.verdict}
    request={{ title: "Ship these fixes?" }}
    onDeny="skip"
  />

  <Task id="fix" needs={{ ok: "triage-approve" }} agent={implementer} …>
</Workflow>

Link 1 — <UI entry> pairs a workflow key to a bundle. When the launcher registers the workflow with an entryFile, the Gateway resolves the entry relative to it, builds it, and serves it at /workflows/triage. smithers ui <run> opens that page with a stable ?runId= deep link, starting a Gateway first if none answers on the local port. The page is same-origin with /v1/rpc, which is why new SmithersGatewayClient() needs no base URL: the Gateway sets a __SMITHERS_GATEWAY_UI__ global carrying workflowKey, mountPath, rpcPath and wsPath before your bundle parses.

Link 2 — the nodeId string is the contract. The "triage-approve" your UI passes to submitApproval is the same string as the id prop on the <Approval>. There is no generated client and no shared type between the two files; a renamed node id is a silently broken button. Keep gate ids as string literals, the same way the runtime already requires stable task ids.

the round trip, end to end
  1. classify finishes and persists outputs.tickets.
  2. <Approval id="triage-approve"> mounts, writes a pending row, parks the lane. The process may exit.
  3. The tab at /workflows/triage?runId=… sees the gate via useGatewayApprovals, and renders the tickets via useGatewayNodeOutput({ runId, nodeId: "classify" }).
  4. A human clicks Approve. submitApproval writes the decision row.
  5. The UI calls resumeRun({ runId }), because the process that parked the lane may be long gone.
  6. The next frame reads the decision; fix, which needs the gate, joins the ready set.

06Who is allowed to decide

Two independent layers, and you generally want both:

  • At the Gateway — writing a decision requires the approval:submit scope. Auth is token, JWT, or trusted-proxy; JWT reads scopes from scope, role from role, and user id from sub. Runs started through the Gateway expose ctx.auth = { triggeredBy, role, scopes, createdAt }.
  • At the node — <Approval allowedScopes> and <Approval allowedUsers> narrow a specific gate further, so “anyone on the team may approve a docs change, only two people may approve a deploy” is expressible in the graph rather than in the UI.

Because the UI is just an RPC client, an unauthorised click fails at the Gateway and not in your component — the button does not need to know the policy, and a hand-rolled UI cannot accidentally widen it.

if you take one thing

Model the human's decision as <Approval> for a verdict or <WaitForEvent> for a payload, keep the context in the upstream task's typed output, and let the UI be a thin reader of both. The gate stays clearable from the CLI when the browser is not around — which is what makes the UI optional rather than load-bearing.

Claims here are grounded in the installed v0.31.0 source, not just the docs bundle: components/src/components/Approval.js (computeDecision narrowing), server/src/gateway.js (validateApprovalDecision, the value unwrap), engine/src/approvals.js (serializeDecision), protocol/src/gatewayRpcTypes.ts (SubmitApprovalRequest), and tui/src/modes/approvalUtils.ts (buildApprovalDecision).

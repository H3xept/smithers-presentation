How to demo the three repos.

Three demos do not fit live in a ten-minute talk. Two of them park durably on a human, which is exactly what makes them safe to pre-warm. So: pre-warm everything, type three commands per demo on stage, and keep the third repo for questions.

The shape

One live moment each, and nothing else

Every repo has a long agent phase and a short human phase. The agent phase is a spinner. The human phase is the demo. Your whole job before the talk is to move each run past the spinner so the stage time is only the human phase.

repoagent phase (pre-warm this)on stagelive time
pricing-apiassess + propose, then it parks on the gatedeny, resume, approve~2:00
todo-clidraft-spec, then it parks on await-editedit the spec, submit, watch~2:30
flaky-monorepothe whole run, twelve lanes, no park (measured 2m 21s)Grafana throughput + token query + scores~1:30, or Q&A only
Why this works and a live launch does not: a parked run is a database row, not a pinned process. You can park it an hour before you speak, close the laptop, and the gate is still waiting when you open it. The pre-warm is not a cheat — it is the feature.

Pre-flight

The timeline before you speak

T-40 smithers oneshot --status must print at least one usable agent. If it does not, no demo runs. Fix credentials first.
T-35 Start the long one. cd examples/flaky-monorepo, then smithers observability --detach and launch the run (stage 2 in its DEMO.md). Measured at 2m 21s for 27 nodes, but Docker image pulls on a cold machine take far longer than the run does.
T-20 Park demo 1. cd examples/pricing-api → smithers up .smithers/workflows/price-change.tsx --detach. Note the run id.
T-20 Park demo 2. cd examples/todo-cli → smithers up .smithers/workflows/spec-then-build.tsx -d. Note the run id.
T-10 Confirm both parked: smithers why <run-id> in each repo. Demo 1 must name gate. Demo 2 must name await-edit.
T-8 Open smithers ui in the todo-cli tab. Leave the browser tab open with the spec already loaded. Do not submit it.
T-5 Screenshot the Smithers Overview dashboard — the Node Throughput and Node Duration panels — plus the Prometheus token query. Those two images are your Docker insurance. There is no trace waterfall to screenshot.
T-2 Font size up. Close every other browser tab. clear all three terminals.
The one thing to write down: both run ids, on paper, next to you. Every stage command needs one, and smithers ps in the wrong directory will not find it.

Terminal layout

Three tabs, one per repo, pre-cd'd

Each repo carries its own .smithers/ pack and its own run store. Every command must run from inside that repo's directory. A command typed one directory up finds no runs, and on stage that reads as a broken product.

tab 1  cd ~/Desktop/lifi/smithers-presentation/examples/pricing-api
tab 2  cd ~/Desktop/lifi/smithers-presentation/examples/todo-cli
tab 3  cd ~/Desktop/lifi/smithers-presentation/examples/flaky-monorepo

Never cd on stage. Switch tabs instead.

Demo 1 · slide 07 · tab 1

01pricing-api — the gate that says no

2 minutespre-warmed and parkedno Docker

The run is already parked on gate. It has read the change request, read both callers of quote(), and drafted a proposal. It has written nothing to the repo.

beat 1 — show that waiting is free

smithers ps
smithers why <run-id>
"This run is not finished and it is not stuck. It is parked on me.
 It has been parked for twenty minutes and it cost nothing to wait,
 because a parked run is a row, not a process."

beat 2 — reject it, with a reason

smithers deny <run-id> --node gate --by leo \
  --note "Mid-cycle accounts must keep the old price until renewal."

smithers up .smithers/workflows/price-change.tsx --run-id <run-id> --resume true
"My rejection and my note are now a decision row in the database.
 The gate uses onDeny=continue, so a rejection is data, not a crash.
 Watch what it does with the sentence I just wrote."

The run re-enters the review loop. revise reads the note and drafts a second proposal that honours it, then the same gate asks again. This is the beat the whole demo exists for — do not rush past it.

beat 3 — approve, and only now does anything change

smithers approve <run-id> --node gate --by leo --note "Mid-cycle rule accepted."
smithers up .smithers/workflows/price-change.tsx --run-id <run-id> --resume true
"Only now does apply run. It writes the code, the price table, and a
 new migration, then runs the tests. Deciding and acting were separate
 nodes the whole time, which is why my rejection was reversible."

beat 4 — the audit trail, if you have ten seconds

smithers timeline <run-id>
"Proposal, rejection, my note, revision, approval. Six months from now
 this is the answer to 'why did the price change?'"
Optional, only with slack: the migration has its own second gate behind --input '{"migrationGate":true}'. Two gates, two owners: approve the price, hold the schema. It needs a fresh run, so it is a bonus, not a beat.

Demo 2 · slide 09 · tab 2 + browser

02todo-cli — you edit the agent's plan

2.5 minutespre-warmed and parkedno Docker

beat 1 — the graph, in one second

smithers graph .smithers/workflows/spec-then-build.tsx
"Draft a spec, then wait for a human. That is the first frame, and it
 rendered without calling a model — the graph is a contract you can
 check before you spend a token."

Verified: graph renders frame zero, so exactly two nodes appear — draft-spec and the await-edit wait node, with its event and correlationId printed as props. implement and test are gated on upstream output and materialise once it exists. Say "the first frame", not "four nodes"; somebody in the room will count.

beat 2 — the UI ships with the workflow

Switch to the browser tab you opened at T-8. If you need it again: smithers ui <run-id>.

"This is not the Smithers dashboard. This page ships with the workflow,
 in .smithers/ui/spec-then-build.tsx, and it is composed from shipped
 components. Connection state, elapsed, tokens, tests passing, and a
 stage strip bound to live node status."

The stage strip shows draft spec done and the run sitting on human edit.

beat 3 — answer the questions the agent could not

The left pane is a real WYSIWYG editor seeded from the draft-spec output. Scroll to Open questions and type over them, out loud:

  • "UTC or local — unresolved" → Store UTC, print local.
  • the recurrence question → The next instance appears immediately on completion.
  • the sort question → list sorts by due date, undated todos last.

Then add one line under New tests: migrating a file with no due dates keeps every id.

"I am not filing a ticket about this. I am editing the document the
 agent is about to build from."

beat 4 — submit, and watch your words become code

Press Submit spec and resume.

"Two things happened. The signal filled the parked node's row, then the
 run resumed. A signal alone does not wake a parked run — you need both,
 in that order, and the UI does it for you."

The stage strip advances to implement. Cycle the right pane: Diff fills in file by file, Tests streams live bun test output into a real terminal, Agent chat shows the transcript of whichever node you select.

beat 5 — land it

smithers inspect <run-id>
"Two rows, two different documents. The agent wrote the first.
 I wrote the second. The code matches mine."
If the UI misbehaves, the same submit is one CLI command. Both keys are required:
smithers signal <run-id> spec.edited --correlation spec-then-build-edit --data '{"markdown":"…","editedBy":"leo"}' then smithers up … --run-id <run-id> --resume true. Omitting --correlation silently parks forever.

Demo 3 · appendix slide 24 · tab 3 + Grafana

03flaky-monorepo — twelve agents, one bill

1.5 minutesneeds Dockerrun verified: 27 nodes, 2m 21s

Keep this one for questions about cost, model choice, or "how do you know it worked". It is the weakest live demo — the run takes too long and it depends on Docker — and the strongest answer to a skeptical question.

beat 1 — the fixture, in one line

bun test packages
"Twelve packages, twelve real defects, and the tests already know what
 correct looks like. One of them also fails to type-check, and the test
 suite cannot see that."

beat 2 — the burst and the bill

Grafana at localhost:3001, the Smithers Overview dashboard. Point at two panels, then one Prometheus query:

  1. Node Throughput and Node Duration. Twenty-seven nodes start inside a two-minute window, and the heatmap shows the whole fan-out landing in one column. Node Success Rate reads 100%.
  2. Tokens by model, at localhost:9090: sum by (model) (smithers_smithers_tokens_output_total). A verified run returned claude-opus-5 9920, gpt-5.6-terra 3091, gpt-5.6-luna 709. Cost is a dimension you query, not a spreadsheet on the side.
Do not promise a span waterfall. Verified on this machine: with SMITHERS_OTEL_ENABLED=1 and the OTLP endpoint set, metrics and logs reach the collector but no spans reach Tempo — GET :3200/api/search returns {"traces":[]}. The dashboard's Traces row stays empty. Also, Active Runs, Active Nodes, and the Tools row are live gauges and read "No data" once the run has finished.

beat 3 — the grade, and the trade

smithers scores <run>
smithers inspect <run> --pool
"The run grades itself, and the grade is a row you can query later.
 inspect --pool tallies attempts by model, so cheap-versus-strong is a
 measurement rather than an opinion — and that one works with Docker down."

Verified output: scores returns Latency 1.00 and Schema Adherence 1.00; the third scorer, the llmJudge named Roll-up Accuracy, starts but never reports, because the run completes before the judge answers. Say "two scorers", not "three". --pool returns codex/gpt-5.6-terra x13, claude-code/claude-opus-5 x12, codex/gpt-5.6-luna x1, codex/gpt-5.6-sol x1.

The comparison, if the question deserves it: the same workflow takes --input '{"fixSeat":"cheap"}' and swaps the whole fan-out onto the cheap seat. Two runs, one dashboard, token panels split by model. Do this before the talk, never during it.

What breaks, and the next command

symptomcausedo this

The gate will not clearSeveral gates pending, so --node is required.smithers why <run> names the node. Pass it to --node.
Deny seems to kill the runYou denied a different gate, or resumed from the wrong file path.smithers timeline <run>, then resume with the exact workflow path and --run-id.
Run parked after a signalSignal name and correlation id must both match.Re-send with --correlation spec-then-build-edit, then resume.
UI is blankGateway not up, or no run for that workflow.Re-run smithers ui <run-id>; it starts a Gateway itself. Fall back to smithers monitor <run-id>.
Grafana panels read "No data"Expected once a run finishes: Active Runs, Active Nodes, and the Tools row are live gauges. The Traces row is always empty — spans do not reach Tempo.Stay on Node Throughput, Node Duration, Node Success Rate, and the Prometheus token query. Or pivot to smithers inspect --pool and scores.
Agent errors mid-demoRate limit or credential.Do not debug on stage. smithers timeline on a finished run tells the same story.
Network dies entirely—graph, ps, why, timeline, inspect, scores all read local state. Run the talk from those.
The rule: never debug live. Every demo has an offline twin that reads persisted state. If a run misbehaves, switch to reading a finished run and keep talking — that pivot is the durability argument.

Reset

Back to a clean fixture, for the next run-through

Demo 1 and demo 2 both write to their repo. Rehearse, then reset, or the second rehearsal starts from changed source.

# pricing-api: apply wrote src/pricing.ts, prices.json, migrations/002_*.sql
# todo-cli:    implement rewrote src/store.ts and src/cli.ts
git checkout -- examples/pricing-api examples/todo-cli

cd examples/flaky-monorepo && smithers observability --down
git checkout -- examples/flaky-monorepo/packages   # the run fixes 11 of 12 packages
bun test packages        # back to 10 pass / 12 fail, plus the one tsc error
Both repos are tracked in git, so one git checkout restores the fixture. Commit before you rehearse, and the reset is a single command between run-throughs.

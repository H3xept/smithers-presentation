Brainstorm · Smithers talk · Aug 2026

Three sub-repos, three flows.

One demo repo per idea. Each sub-repo is small enough to read on a projector in ten seconds, and each one produces work that genuinely needs the flow it showcases. That second constraint is the whole design: an approval gate on a change nobody would care about teaches the audience that gates are ceremony.

Read this as a design record, not a manual. It is the pass that chose the three demos, written before any of them existed — which is why the "considered and cut" section at the bottom is the useful half. Everything here has since been reconciled against the repos as built and against a live smithers@0.31.0, and where reality disagreed with the plan, the plan lost: the Tempo waterfall this document originally promised does not exist, and the callout in §02 explains what replaced it. For the commands you would actually type, read the runbook and each repo's DEMO.md.

Example 01 · human approval gates

01pricing-api — the gate that says no

Approvaldeny → revise loop onDeny="continue"blast radius13 files

A tiny billing service with a public price table and one SQL migration folder. The change request is deliberately a money-and-schema change, so the audience feels why a human stands in the middle of it.

examples/pricing-api/ src/ pricing.ts # tiers + the one exported quote() function pricing.test.ts # 5 tests, green routes.ts # GET /quote, POST /subscribe migrations/ 001_init.sql consumers/ checkout.ts # calls quote() — this is the blast radius reporting.ts # calls quote() too prices.json # the numbers a human must sign off on CHANGE-REQUEST.md # the request the workflow reads package.json · README.md · DEMO.md .smithers/workflows/price-change.tsx

the flow

taskread request + map callers
→
taskdraft code + migration
→
approvalhuman: apply or reject
→
on denyrevise with the reason
↺
taskapply + bun test

The hero moment is the deny, not the approve. You reject with a written reason — "don't break checkout.ts, ship it behind a flag" — the workflow feeds that string back into the revise node, and the second proposal is non-breaking. That proves the gate is a typed input to the graph, not a checkbox in front of a script.

demo beats (~2 min)

0:00 Show prices.json and the two consumers. Thirteen files in the whole repo, no explanation needed.
0:20 Run is pre-warmed and already parked at the gate. smithers why <run> prints exactly what it is waiting for.
0:40 Open smithers monitor. The approval panel shows the diff plus the agent's blast-radius note.
1:10 smithers deny <run> --node gate --note "…", then resume with --run-id <run> --resume true. Watch the revise node wake up.
1:40 smithers approve <run> --node gate. Tests go green in the node output.
Why this beats a generic gate demo: the deny path is the only way to show that a human decision changes the plan. Everyone has seen a confirm dialog. Nobody has seen a plan re-derive itself from a rejection.

bonus, if there is slack

The second gate on the migration is already built, behind an optional input: launch with --input '{"migrationGate":true}' and the schema change needs its own decision. Kill the process while a gate is parked, then resume, and durability plus approval land in one beat — a parked gate is a persisted node, not a pinned process.

Example 02 · observability

02flaky-monorepo — twelve lanes and one liar

OTel metricstoken cost retriesscorerstimeline12 tiny packages

Observability is boring on a three-node happy path. It gets convincing when there is width, failure, and cost. So: twelve trivial packages, each with one real defect, fanned out in parallel. Eleven or twelve of the twenty-two tests fail on a clean checkout, and the count moves between runs because one package races the clock.

examples/flaky-monorepo/ packages/ pkg-01 … pkg-12/ # each: index.ts + index.test.ts + package.json # one small pure function, one real defect, ~15 lines # pkg-07 is wall-clock flaky: failed 10 of 20 consecutive runs, measured # pkg-11 also has a real tsc error at index.ts(10,9) tsconfig.json · package.json · README.md · DEMO.md .smithers/workflows/harden-packages.tsx

the flow

→
parallel ×12fix + test each package
→
retryfailures re-run, bounded
→
scorers ×3schema · latency · llmJudge
→
taskroll-up report

what the audience actually looks at

  • The burst, in Grafana. Node Throughput and Node Duration on the provisioned Smithers Overview dashboard: twenty-seven nodes starting inside a two-minute window, the whole fan-out landing in one column of the heatmap.
  • Cost, split by model. The dashboard ships no token panel, so query Prometheus directly: sum by (model) (smithers_smithers_tokens_output_total). A real run returned claude-opus-5 9920, gpt-5.6-terra 3091, gpt-5.6-luna 709.
  • smithers scores <run> — quality as a number rather than an impression. Two deterministic rows land, Latency and Schema Adherence; the llmJudge third scorer starts but never reports, because the run completes before the judge answers.
  • smithers inspect <run> --pool — attempts tallied by engine and model. The same cost story with Docker down.
  • smithers timeline <run> — the fork tree, if you also demo a replay.
  • smithers what <run> — the cheap narrated recap, as the "I do not want to read events" answer.
Do not promise a trace waterfall. This section originally planned one, and it does not exist. Verified against a real run: with SMITHERS_OTEL_ENABLED=1 and the OTLP endpoint set, metrics and logs reach the collector but no spans reach Tempo — GET :3200/api/search returns {"traces":[]} while Prometheus holds the run's metrics in full. The width of the fan-out is provable from the throughput panel and from smithers inspect, not from a span tree.
The comparison trick: run the same workflow twice — --input '{"fixSeat":"cheap"}' swaps the whole fan-out onto the cheap seat — then put both runs on one Grafana dashboard, where the token series split by model. Compare the two report grades side by side with smithers scores <run> --node report. Two pre-recorded runs, zero live risk. Do not quote a cost ratio you have not measured on the day; the point is that the trade is measurable, not that it is any particular number.

setup cost

smithers observability --detach brings up the Docker stack: Grafana on :3001 (anonymous viewer, admin password admin), Prometheus on :9090, Tempo on :3200, Loki on :3100, and the OTLP HTTP intake on :4318. Loki is in the stack even though smithers observability --help does not mention it. Launch the run with both SMITHERS_OTEL_ENABLED=1 and OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318 — the endpoint alone exports nothing — and pass --max-concurrency 12, or the engine caps the fan-out at four and the throughput panel looks narrow. That stack is the one hard dependency in the whole set, so start it early and screenshot the dashboards while a run is in flight: Active Runs, Active Nodes and the Tools row are live gauges and read "No data" afterwards. graph, scores, timeline, inspect, and why all read local state and need no Docker.

Example 03 · custom workflow UI

03todo-cli — the human edits the agent's artifact

MarkdownEditorTerminal StageStripDiffHunksChatComposer~7 files

The CLI cannot show mid-run collaboration, which is exactly the gap a custom UI fills. So build the one interaction that is impossible anywhere else: the agent drafts a spec, the human edits the rendered document in the browser, and the edited text is what the implementation node receives.

Data comes from createGatewayReactRoot plus useGatewayRun / useGatewayNodeOutput / useGatewayActions. Submitting the edited spec is submitSignal then resumeRun: a signal alone does not wake a parked run, and it must carry signalName as well as correlationKey or no waiter ever matches. The workflow and the UI import both strings from one shared contract file so they cannot drift.

Run against the shipped grader, gradeWorkflowUiSource, this bundle came back { passed: true, score: 1, violations: [] }. No hand-rolled pills, tables, or colors.

demo beats (~2 min)

0:00 smithers ui <run>. The spec is already drafted and waiting.
0:15 Edit one line of the spec live — change "due dates" to "due dates in UTC only". Submit.
0:45 Implementation node wakes. Diff tab fills in. Terminal tab streams the test run.
1:30 Point at the KpiStats. Close on: this whole surface is one .tsx file.
Why the spec editor and not a dashboard: a dashboard shows you a run. An editor makes you part of it. The moment your typed sentence provably steers the next agent, the "durable control plane" claim stops being a slogan.

Shared conventions

Make all three interchangeable

One layout, three times

Every sub-repo: README.md (5 lines max), a real bun test that passes on a clean checkout, and its own .smithers/. No shared root package — each one is independently clonable, because "copy this folder" is the takeaway you want.

Pre-warm everything

A fresh run is ten minutes of spinner. Before the talk, launch all three, then park #1 at its gate and park #3 at its spec editor. Demos start on a run that already has real output.

Offline fallback per example

graph, timeline, inspect, why, and scores read local state. For #2, screenshot Grafana before the talk and keep the images next to the deck.

Each has a DEMO.md

Repo → flow → exact commands in order → the one sentence to say. So the talk is reproducible by someone who is not you, and so you can hand the repos out afterwards.

What I rejected, and why

ideaverdict
Destructive-script runbook
gate before drop-stale-tenants.ts		Visceral, but the gate is the only content. No deny→revise path, so it teaches "confirm dialog". Good as a 20-second aside inside #1.
Dependency-bump demoRealistic and dull. The approval has no stakes an audience can feel in ten seconds.
Alert-suppressor for observabilityNeeds fake alert history to be credible. Setup cost exceeds the payoff versus a parallel fan-out you can literally point at.

One repo, three workflowsTempting for maintenance. Rejected: three separate folders make "copy the closest example" the obvious next action for the audience.
The one risk to watch: all three examples want a real coding agent doing real work, so all three are non-deterministic on stage. Mitigation is the same each time — pre-warm, park at the interesting node, and keep the recorded run as the fallback. Never let the first live agent turn of the talk be the thing the point depends on.
